## v3.3.63 更新重點：修復頂部版面失衡（Logo 錯位、標語擠成一團、header 過高壓縮下方空間）

- **根本原因**：`header` 用 `align-items:flex-end`（左右兩欄底部對齊）。這在右欄
  只有一兩行內容時沒問題，但右欄後來陸續加了 API 狀態列、標語、快速跳轉連結，
  變成 3 段內容，比左欄（標語小字＋Logo，只有 2 段）高出不少；底部對齊的結果，
  是左欄的 Logo 被往下推、才能讓兩欄的「底部」對齊，造成 Logo 明顯比右欄內容低、
  版面失衡，也讓整個 header 看起來比實際需要的還要高，把下面 STEP 1/2/3 的可用
  空間往下擠壓。
- **修法**：改成 `align-items:flex-start`（兩欄頂端對齊），Logo 回到跟右欄頂端
  同高的位置，header 整體高度也會自然收斂到剛好符合內容需要的高度。
- **標語文字擠成一團**：原本 300px 的寬度上限太窄，讓標語被迫換成 3 行很短的
  句子，看起來像被硬擠在一起。放寬到 420px、行距也拉開一點（1.6→1.7），讓文字
  換行換得更自然。

### 驗證方式
- HTML 標籤配對、CSS 大括號配對：全部正確
- 後端完全沒有變動（檔案雜湊值跟上一版一致）
- ⚠️ 純視覺調整，這個沙盒環境沒有瀏覽器可以實際渲染確認效果，建議實際看一次

## v3.3.62 更新重點：修復後台管理視窗實際被限制在 520px 寬的 CSS 優先權 bug

- **問題**：後台管理視窗一直被限制在最大 520px 寬、86vh 高，比想像中更窄——原因是
  這個視窗的 HTML 同時掛了 `.modal-box`（所有彈出視窗共用的基礎樣式，裡面訂了
  `max-width:520px`、`max-height:86vh`）跟 `.admin-modal-box` 這兩個 class。這兩條
  CSS 規則的「優先權」（specificity）完全相同，瀏覽器規則是優先權相同時「後面
  宣告的規則獲勝」——而 `.modal-box` 剛好寫在 `.admin-modal-box` 後面，所以
  `max-width:520px` 其實從頭到尾都在悄悄生效，v3.3.56 想放寬到 920px 的設定根本
  沒真正起作用。加上 v3.3.56 上線的拖曳調整大小功能，使用者不管怎麼拖曳右下角
  把手，視窗都被卡在 520px 寬，導致像登入紀錄這種欄位較多的表格，怎麼調整視窗
  大小都看不到全部欄位。
- **修法**：改用 `.modal-box.admin-modal-box`（同時寫兩個 class 的選擇器）——優先權
  比單一 class 選擇器更高，確保無論 CSS 規則先後順序為何，都一定會蓋掉
  `.modal-box` 原本的 520px／86vh 限制，寬高完全交給 JS 決定（開啟時的預設大小、
  拖曳調整大小時的即時上限），可以把視窗拉到幾乎跟整個瀏覽器視窗一樣大。
- 只影響後台管理視窗，API 金鑰設定視窗（只有 `.modal-box`、沒有
  `.admin-modal-box`）維持原本置中彈出、520px 上限的樣子，不受影響。

### 驗證方式
- CSS 選擇器優先權（specificity）的計算邏輯已驗算確認：組合選擇器
  `(0,2,0)` 高於單一class選擇器 `(0,1,0)`，保證無論規則宣告順序為何都會生效
- HTML 標籤配對、CSS 大括號配對：全部正確

### v3.3.57：修復「自動存檔失敗」的根本原因 + PDF 擷取文字逐字空格問題
- **自動存檔失敗（根本原因）**：原本用的 `window.storage` 其實是 Claude.ai 的
  Artifact 沙盒環境專屬 API，不是瀏覽器原生支援的功能。這個工具部署成一般網站後，
  只要不是在 Claude.ai 的預覽畫面裡執行，`window.storage` 根本不存在，呼叫
  `window.storage.set(...)` 一定會直接丟出例外——這代表自動草稿保存這個功能，
  從一開始部署成真正網站後就沒有真的成功運作過。改用瀏覽器原生支援的
  `localStorage`，資料留在使用者自己的瀏覽器裡，不會上傳到任何伺服器。
- **PDF 擷取文字逐字空格**：原本把 pdf.js 擷取出來的每一小段文字都用空白字元接起來，
  對「每個中文字是獨立一個片段」的 PDF（很常見）會導致「個 人 資 料」這種每個字
  中間都被空一格的擷取結果。改成依照每個文字片段實際的座標位置判斷，只有真的有
  明顯間隔（例如英文單字之間）才補上空白，同一行內間隔很小就直接接起來。

## v3.3.54 更新重點：模擬10位不同身分使用者測試，找到1個重大缺失+1個小缺失

### 🔴 重大缺失：後台下載履歷的檔名完全錯誤（v3.3.46 的遺留 regression）
- **問題**：後台「下載」履歷時，檔名是用 `key.split('-').slice(2).join('-')` 從儲存
  key 反推出來的——這是 v3.3.42 之前「key 裡真的有包含原始檔名」時代留下的寫法。
  v3.3.46 把 key 格式改成 `resume-verified-${email}` / `resume-anon-${ip}`（不再
  包含檔名）之後，這行邏輯就已經過時，卻沒有跟著更新，一直遺留到現在。
  實際影響：管理者下載下來的檔案會被命名成類似「alice@example.com」這種**沒有副
  檔名**的怪檔名，作業系統不知道這是 PDF 還是 Word，可能無法直接雙擊開啟。更麻煩的
  是：伺服器端其實已經透過 `Content-Disposition` 標頭正確設定好檔名，但前端 `<a>`
  標籤設了 `download` 屬性，瀏覽器會優先用這個屬性命名、蓋掉伺服器端本來對的設定——
  等於是「做錯、還蓋掉了本來對的」。
- **修法**：後台列表渲染時本來就已經有正確的原始檔名（`f.filename`，用來顯示在表格
  裡），直接透過 `data-download-filename` 屬性把這個檔名傳給下載函式使用，不再嘗試
  從 key 反推。

### 🟡 小缺失：`escapeHtml()` 有兩套獨立維護、跳脫規則不一致的版本
- **問題**：`shared-helpers.js` 的 `escapeHtml()` 跟 `admin.js` 的 `escapeAdminHtml()`
  幾乎一模一樣卻各自維護，`escapeAdminHtml` 多跳脫了單引號、`escapeHtml` 沒有。目前
  程式碼裡所有 HTML 屬性都統一用雙引號包住，所以實務上還不構成可被利用的漏洞；但兩套
  規則不一致本身就是技術債，日後如果不小心在某處用單引號包屬性，AI 產生的內容剛好
  包含單引號時就可能造成破版，屬於「防禦深度不足」的小缺失。
- **修法**：統一成一套（`escapeHtml`，已補上跳脫單引號），`admin.js` 不再重複定義，
  改呼叫共用的那一份。

## v3.3.49 更新重點：5 項程式邏輯缺失修復（併發鎖、過期偵測、版型高亮、草稿遺失風險）

## v3.3.46 更新重點：5 項缺失修復（儲存空間、資料衝突、程式架構、登入體驗、Word 上傳）

這個版本一次處理了 5 個先前盤點出來的問題，彼此獨立、互不影響：

### 1. 匿名上傳無限制，可能塞爆儲存空間 → 改成「同一來源只留最新一份」
- **問題**：`upload-resume.mjs` 原本每次上傳都用 `Date.now()` 當 key 的一部分，同一個人
  （或同一個繞過登入牆的來源）每上傳一次就多存一筆，永遠不會變少。
- **修法**：已登入者改用 email 當固定 key，未登入（含繞過登入牆）者改用來源 IP 當固定 key。
  同一人／同一來源再次上傳會直接覆蓋自己前一份，系統裡永遠只留「每個來源最新的一份」；
  不同來源仍各自保留一筆，管理者還是看得出有幾個不同來源在繞過登入牆。另外加了
  `MAX_INDEX_ENTRIES`（5000 筆）當保險上限，避免極端情況下持續增長到失控。

### 2. 後台資料寫入沒有防止衝突，可能互蓋 → 改用條件式寫入＋重試
- **問題**：登入紀錄、履歷索引都是「整包讀取 JSON → 修改 → 整包寫回」，兩個請求前後腳
  同時處理時，其中一筆可能被另一筆覆蓋、憑空消失。
- **修法**：新增共用工具 `netlify/lib/blob-json.mjs`，用 Netlify Blobs 支援的
  `onlyIfMatch`（ETag 條件式寫入）搭配自動重試，偵測到衝突時會重新讀取最新資料再試一次，
  最多重試 5 次。已套用到 `upload-resume.mjs`、`record-login.mjs`、`admin-resume-file.mjs`
  三支 function。`package.json` 的 `@netlify/blobs` 已升級到 `^10.0.0`（條件式寫入從這個
  版本才開始支援）。
  > 這個檔案刻意放在 `netlify/lib/` 而不是 `netlify/functions/` 裡面，是延續 v3.3.42
  > 就有的既有考量——避免 Netlify 把 functions 目錄底下多出來的檔案誤判成另一個新的
  > function 端點。esbuild 打包時仍會把這裡的程式碼正常打進呼叫它的 function 裡。

### 3. 3500 多行擠在同一個 `<script>` → 拆成 13 個獨立檔案
- **問題**：所有前端程式碼都擠在 `index.html` 唯一一個 `<script>` 標籤裡，過去曾發生過
  「某一小段出錯，導致後面所有按鈕都沒反應」的重大臭蟲，日後維護、除錯風險都很高。
- **修法**：依功能拆成 `js/` 資料夾底下 13 個檔案（登入、後台管理、共用工具、API 金鑰、
  AI 呼叫層、履歷與草稿、頁籤總控、5 個功能頁籤、初始化），用多個 `<script src>` 依原本
  順序依序載入。**這次刻意沒有改成 ES module**（`type="module"`），而是維持跟原本一致的
  「多個 `<script>` 共用同一個全域作用域」寫法——這樣完全不需要更動任何函式或變數的呼叫
  方式，行為上與拆分前 100% 相同（已用逐字比對確認），同時仍然達到「某一個檔案載入時
  出錯，不會拖累在它之後載入的其他檔案」的目的，風險比改寫成 ES module 低很多。
  之後要新增功能或修 bug，直接找對應的檔案即可，不用在三千多行的大檔案裡搜尋。

### 4. 一進站就被登入牆整個擋住 → 登入前先看得到工具能幹嘛
- **問題**：原本登入畫面只有一個標題、一句話跟一顆登入按鈕，完全看不到工具長怎樣，容易讓
  還沒體驗過的人直接關掉分頁離開。

- **問題**：上傳欄位寫死只接受 `application/pdf`，但工具本身卻能「輸出」Word 檔，

  - `<head>` 新增 mammoth.js（`mammoth.browser.min.js`，純瀏覽器端函式庫）。
  - 上傳欄位與拖曳區改成同時接受 `.pdf` 與 `.docx`，用副檔名＋MIME type 雙重判斷檔案

  - 後台下載履歷時，`content-type` 改成依副檔名判斷（PDF / docx 各自對應正確的
    MIME type），避免下載到的 Word 檔被瀏覽器誤判成損毀的 PDF。

## v3.3.44 更新重點：後台管理表格「瀏覽器」欄位太長，撐爆版面

### 問題
後台管理跳出的視窗裡，登入紀錄表格的「瀏覽器」欄位直接顯示完整的 User-Agent 原始字串
（例如 `Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 ...`），字串很長又設定
`word-break:break-all` 讓它整段換行顯示，導致每一列的高度被撐得非常高，管理者要一直往下滑
才能看完幾筆紀錄，版面很亂。

### 修法
- 新增 `summarizeUserAgent()`，把落落長的 User-Agent 字串轉換成精簡好讀的摘要，例如
  `Chrome 128 · Windows`、`Safari 17 · iOS`、`Firefox 128 · Linux`，只顯示瀏覽器名稱、
  主版本號、作業系統。
- 表格欄位改成單行顯示＋超出寬度用「…」省略（`white-space:nowrap` + `text-overflow:ellipsis`），
  不會再逐字換行撐高列高；把滑鼠移到欄位上（`title` 屬性）仍可看到完整原始 User-Agent 字串，
  之後真的需要逐字比對時不會遺失資訊。
- 「⚠️ 異常上傳」表格裡的「來源頁面」（Referer/Origin，通常也是一整串網址）比照辦理，
  同樣單行顯示＋省略號，滑鼠移上去看完整網址。

## v3.3.43 更新重點：不管有沒有登入，只要上傳履歷就記錄下來

### 為什麼要這樣改
v3.3.42 修好後台「一律未登入」的臭蟲之後，你希望能進一步確認：**登入牆本身有沒有其他漏洞、
能不能被繞過**。原本 `upload-resume.mjs` 的邏輯是「沒有有效登入身份就直接回傳 401、什麼都
不記錄」——這代表萬一真的有人繞過前端登入牆去呼叫這支 API，後台反而完全看不到任何蛛絲馬跡。

### 這次改了什麼
- `upload-resume.mjs`：不再因為沒有登入身份就拒絕存檔，改成**一律記錄**，並多存一個
  `verified`（是否通過有效的 Google 登入）欄位，以及 IP、瀏覽器（User-Agent）、來源頁面
  （Referer/Origin）等診斷資訊。
- 前端 `uploadResumeToServer()`：不再「沒有登入 Token 就直接放棄上傳呼叫」，一律送出，
  有 Token 就附上，沒有就讓後端標記為未驗證。
- 後台管理畫面：新增一個獨立的「⚠️ 異常上傳」區塊，把 `verified:false` 的紀錄
  （代表沒有通過登入驗證就成功上傳）跟正常使用者分開列出，附上 IP／瀏覽器／來源頁面，
  方便你比對是否真的有人繞過登入牆，或找出前端判斷邏輯還有哪裡沒堵住。

### 重要說明：這不是「降低安全性」
- 下載、刪除履歷、讀取後台清單這幾個管理功能，**仍然**只有 `felix670131@gmail.com`
  能用（`admin-data.mjs`、`admin-resume-file.mjs` 的權限檢查完全沒變）。
- 放寬的只有「上傳履歷」這個單一動作的記錄方式，目的是把potentially 繞過登入牆的行為
  「攤在陽光下」讓你看得到，而不是讓沒登入的人能存取別人的資料。
- 如果後台的「⚠️ 異常上傳」區塊之後真的出現資料，代表登入牆確實有辦法被繞過，
  屆時可以把對應的 IP／瀏覽器／來源頁面資訊交給我，我再往下追查前端登入判斷的漏洞。

## v3.3.42 更新重點：修復後台管理一律顯示「讀取失敗：未登入」

### 根本原因
`netlify/functions/` 底下四支 function（`admin-data.mjs`、`record-login.mjs`、
`upload-resume.mjs`、`admin-resume-file.mjs`）都是用新版（Modern / V2）的
`export default async (req, context)` 簽章撰寫，但判斷登入者身份時卻用了：

```js
const user = context.clientContext && context.clientContext.user;
```

這是**舊版（Lambda-compatible / V1，`exports.handler = async (event, context)`）**
才適用的寫法。Netlify 官方文件（[Use Identity in functions](https://docs.netlify.com/manage/security/secure-access-to-sites/identity/use-identity-in-functions/)）
明確指出：V2 簽章下 `context.clientContext` **不會**自動帶入 Identity 使用者資料，
新版 function 要改用 `@netlify/identity` 套件的 `getUser()`。

也就是說：
- 這**不是** session 過期、也**不是** Netlify 平台本身不穩定造成的偶發問題，而是每一次
  呼叫都必然會回傳「未登入」的結構性問題——不管 Google 帳號有沒有登入成功、Token 新不新。
- 除了後台管理讀不到資料以外，**每次登入的紀錄（`record-login`）與使用者上傳的履歷 PDF
  備份（`upload-resume`）也同樣因為這個原因從未真正寫入過**，只是因為前端這兩支呼叫是
  「不影響主要功能」的背景動作、失敗時只印 console，畫面上完全看不出來，所以先前沒被發現。

### 修法
四支 function 都改用官方建議的 `@netlify/identity` 的 `getUser()` 取得登入者：

```js
import { getUser } from '@netlify/identity';
const user = await getUser(); // 自動讀取前端送來的 Authorization: Bearer <token>
```

並保留 `context.clientContext.user` 作為備援（`getUser()` 失敗或回傳空值時才會用到），
避免未來 Netlify 行為再調整時，整個後台又無預警失效。

`package.json` 已新增 `@netlify/identity` 相依套件，部署時 Netlify 會自動安裝，
不需要手動處理。

### 順便補上的防呆：自動重試一次
後台管理面板呼叫 `admin-data` 若收到 401，前端會**自動用強制刷新過的 Netlify Identity
Token 重試一次**，才會顯示「讀取失敗」。這是為了因應「Token 剛好在快過期的時間點被使用」
這種單純的時間差狀況，讓管理者不必手動登出再登入。（這次的「未登入」本身跟 Token 過期
無關，但這道防呆能避免以後真的遇到 Token 過期時又要重新走一次登入流程。）

### 部署時請注意：避免互蓋檔案
這次版本是獨立資料夾 `zhitou-jobsight-v3.3.42`，**不會**跟 v3.3.22 的檔案共用檔名之外的
任何東西。部署時請用這個版本**完整取代**舊版的所有檔案（`index.html`、`netlify.toml`、
`package.json`、整個 `netlify/functions/` 資料夾），不要只挑幾個檔案覆蓋，避免新舊版本的
`package.json`（相依套件不同）或 functions 混在一起造成部署失敗或行為不一致。
